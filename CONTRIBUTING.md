# Contributing and release process

## Local checks

- Frontend: from `frontend/`, run `npm ci`, `npm run lint`, and `npm run build`.
- Backend security tests: from the repository root, run `python -m pytest backend/tests` and `python -m compileall -q backend`.
- Model evaluation: follow the data and preprocessing protocol in `README.md`; run `python train.py` from `backend/`. Keep generated reports in `backend/saved_models/evaluation/` with the exact code revision and dataset provenance. Never publish patient data or private credentials in a commit or report.

## Pull requests

1. Create a focused branch from `main`; do not commit directly to `main`.
2. Explain the behavior change, data/schema impact, and verification performed.
3. Include or update tests and migration files for database changes. Do not disable RLS to make a test pass.
4. Require CI and a maintainer review before merging. Changes affecting patient information, authentication, model evaluation, or deployment configuration require explicit review by the relevant owner.

## Releases

1. Merge the reviewed, green pull request to `main`.
2. Create a version tag (`vMAJOR.MINOR.PATCH`) on the reviewed commit and publish GitHub release notes describing user-visible changes, schema migrations, operational configuration, and known limitations.
3. Confirm the Vercel frontend and Render backend deployments use the same release commit and that required environment settings are present. Never place secrets in release notes or repository files.
4. For model releases, attach evaluation JSON/CSV generated by the documented hold-out procedure, record the dataset provenance and code revision, and state that results do not establish clinical validity. Do not claim medical-device readiness.
5. Verify the live health endpoint and sign-in/profile isolation using separate test accounts before announcing the release. Do not use real patient information for release verification.
